# Beli Group Taste-Match Explore: Decision-Pipeline Experiment

**Experiment plan and results-report requirements**  
Version 1.0 · October 4, 2026

Companion product document: [Beli Group Taste-Match Explore PRD](Beli_Group_Taste_Match_Explore_PRD.md).

## 1. Purpose and relationship to the PRD

Compare the Clef pipeline against a simple general-purpose LLM baseline using the same real NYC restaurant snapshot, synthetic taste profiles, group scenarios, travel estimates, and simulated availability. Determine which method the prototype should use, and produce a presentation-ready report for Beli's founders from actual measurements.

The product PRD defines the participant experience, constraint policy, one-round clarification limit, conditional host decision, and single-restaurant output. This plan defines how to evaluate implementations of that product. It does not authorize expanding the UX or changing a diner's requirements to make a method perform better.

A Clef win is a hypothesis, not a deliverable. A baseline win, a provisional choice, or an inconclusive result is valid when supported by the evidence. No experiment results or human assessments have been generated by writing this plan.

## 2. Methods and shared conditions

| Method | Decision implementation | Relevant distinction |
| --- | --- | --- |
| Clef pipeline | Clef evaluates fit per diner and restaurant; code aggregates fit and controls selection; a general LLM interprets input and writes natural wording | Bounded decision scores and explicit group-selection policy |
| Simple LLM baseline | One general LLM prompt per decision phase selects a restaurant or an allowed next action from the supplied state | Direct prompted decision without Clef or a separate per-diner scoring pipeline |

Implement both through the interface in the PRD. Give both the same hierarchy of current requests, historical taste, hard requirements, fairness priorities, and product stage limits. Keep the baseline competently prompted; do not disadvantage it by withholding facts, clarification opportunities, or safeguards.

The common application supplies transcription, normalized input with original text, restaurant evidence, profiles, travel estimates, availability fixtures, deterministic feasibility checks, legal-stage enforcement, and result-card rendering. Count all serving costs even when a component is shared. Preserve each method's raw proposal before the final guard. Do not silently switch methods during a benchmark run.

The PRD contains the Clef API integration and group-selection policy. Freeze their exact implementation, together with the baseline prompt, before the held-out test.

## 3. Experiment protocol

### A. Commit the protocol before measuring the held-out set

Create a machine-readable protocol and dataset manifest. Commit or hash the restaurant snapshot, profile snapshot, scenario splits, fixture seed, prompts, rubric, scoring code, model settings, retry policy, and architecture decision rule. Fix the comparison's budget in the protocol. Log any change made after the freeze as a new experiment version.

Use 60 group scenarios: 20 development and 40 held-out test scenarios. Balance group sizes 2–6 across both splits. Cover the following ten families, approximately six scenarios per family. Keep near-duplicates and variants of the same base scenario in the same split.

| Scenario family | Failure the experiment should expose |
| --- | --- |
| Clear shared preferences | Needless questions or weak choices in easy situations |
| Mixed cuisine/occasion preferences | Sacrificing one diner for the majority |
| Budget versus atmosphere | Treating “nicer” as expensive or ignoring a cap |
| Dietary needs and missing verification | Assuming an unsupported accommodation |
| Different starting areas and travel priorities | Optimizing only for the host or nearest diner |
| Sparse input and unknown budget/location | Inventing requirements or asking too many questions |
| Current request versus historical taste | Letting history override what somebody wants today |
| Hours, party size, and simulated slots | Selecting a known closed or unavailable restaurant |
| Infeasibility and response timeouts | Inventing a match or treating silence as permission |
| Noisy transcripts, order changes, and irrelevant instructions | Misreading spoken input or obeying text that conflicts with product rules |

Include at least eight genuinely infeasible scenarios, at least six in the test set, based on the frozen data and explicit constraints. Distinguish true infeasibility from missing evidence and an operational error. Prelabel expected constraint checks, available clarification facts, and any correct no-match outcome before model runs. Do not label one restaurant as the unique correct answer when several meet the scenario well.

Synthetic scenario preferences are appropriate for controlled tests; they are not feedback from real Beli users. The held-out test should not become a source of prompt tuning. If a defect requires tuning after seeing it, move the work to a new development cycle and collect a fresh test set for confirmation.

### B. Run two complementary comparisons

**Fixed-state restaurant selection:** Freeze the normalized group state after any supplied clarification. Disable additional questions for this track. Send the same restaurant records, candidate IDs/order, original text, profiles, travel estimates, and availability to both methods. This isolates the decision layer. Run each of the 40 test scenarios three times per method: 240 decision runs. Use identical recorded candidate-order and participant-order permutations for each paired run, balance execution order, and record seeds where the provider supports them. Cluster repeats by scenario during analysis.

**Complete product flow:** Replay all 40 test scenarios once per method from initial submission through clarification, conditional host intervention, and final output: 80 sessions. Use predefined scenario answers and timeout events. A simulator may answer a question only from prewritten facts, never invent a convenient concession. Unanswerable or extra questions receive the predefined unknown/timeout behavior. Log the extra effort each method asks of diners.

Develop freely on the 20 development scenarios before freezing. The counts above are minimum final test runs, not a prohibition on development testing. Report both tracks separately: an isolated decision-layer result does not prove the full UX works better. If a runtime budget prevents completing the protocol, report the actual sample and the unfinished portions instead of quietly reducing it.

### C. Evaluate independently

Use deterministic checks against each scenario's requirements and the frozen facts for restaurant identity, hard constraints, availability, party size, hours, legal stages, and correct abstention. Preserve original requirements; only an explicit submitted clarification from their owner can change an effective requirement. Log that change and evaluate both whether it was authorized and whether the final choice respects it. Silence or a host answer never counts as a waiver. Check both raw proposals and delivered outcomes. A shared guard can make final violations zero for both arms; report how often it had to block each arm and whether recovery succeeded.

For subjective fit, do not reuse Clef's scores or the baseline's self-assessment. Use a blinded evaluator given the scenario, diner preferences, and selected restaurant facts, without method names or internal scores. Apply the same 0–4 fit rubric independently to each diner. If automated, use a separately configured judge model, preferably from a different model family, keep its settings fixed, and label the results **model-judged**. Cache only identical evaluation items; do not choose a judge based on favorable outcomes.

Generate a blinded review packet for all 40 test scenarios using the first pre-scheduled run, not the best run. Randomize A/B order. Include scenario information, the restaurant facts, and a common result-card format. Request independent assessments from two human reviewers if available, including ties and “neither acceptable.” Collect preference, per-diner fit, explanation quality, and reasons. Record disagreement and missing responses; do not invent or impersonate reviewers. Human review can be collected after the automated experiment without blocking delivery of a clearly provisional report.

Do not count real dinner enjoyment, participant satisfaction, or retention as measured unless a real user study actually occurred. Likewise, simulated flow timeouts are not observed human completion behavior.

### D. Metrics and denominators

| Metric | Definition and reporting |
| --- | --- |
| Acceptable group rate, primary quality metric | Among scenarios with verified feasible options, share of runs returning a valid restaurant independently rated ≥2/4 for every diner. Abstention or operational failure on a feasible case is a failure. |
| Hard-constraint violations | Count and rate against effective explicit requirements, with owner-authorized changes audited against the originals; report raw proposals and final deliveries separately, by constraint type. |
| Weakest-diner fit | Independent minimum per-diner score for the selected restaurant; failures on feasible cases receive 0. Report mean group fit separately. |
| Correct no-match rate | Share of prelabelled infeasible cases correctly declining to recommend; report false no-match rate on feasible cases separately. |
| Evidence grounding | Unsupported factual claims, wrong IDs, or incompatible price/travel/availability claims; distinguish verification failures from absent facts. |
| Clarification burden | Questions per diner/session, needless questions, unresolved ambiguities, and conditional host-call frequency in full-flow sessions. |
| Runtime reliability | Completed valid outcomes, provider errors, invalid schemas, guard rejections, and retries. Keep failed runs in denominators. |
| Latency | p50/p95 decision-phase and full automated processing time, including retries; exclude human/fixture waiting and show timeouts separately. |
| Cost | All transcription, normalization, decision, retry, and explanation calls per session; show decision-only cost too. Separate evaluation-judge cost from serving cost. |
| Stability | Within-scenario choice/action agreement across repeats and sensitivity to participant/candidate order. Different equally good choices are not automatically errors. |
| Human preference, if collected | Blinded A/B wins, losses, ties, neither acceptable, reviewer agreement, and actual sample size. |

Show counts as well as percentages. Use a paired analysis and 95% confidence intervals; resample whole scenarios, keeping repetitions together. Pre-specify the bootstrap seed and interval method. Stratify by group size and scenario family, but treat small subgroup results as exploratory. Report infeasibility metrics separately from the feasible-case quality metric.

Use observed usage and a dated pricing source to estimate API spend when billing is unavailable. Label estimates and missing components. Do not report zero cost when a provider did not expose usage. Separate cold/warm cache behavior and external outages from decision quality.

### E. Precommitted architecture selection rule

Safety and grounding come first. Any delivered hard-constraint violation or invented reservation/restaurant requires diagnosis before declaring that method demo-ready. Fix genuine implementation defects on the development set, then run a new frozen comparison if needed. Both methods may fail this gate; the report must allow that outcome.

For methods that pass the final-delivery checks, define a practical quality difference as **5 percentage points** in acceptable group rate. Prefer a method for quality when its paired advantage is at least that large and its 95% interval excludes zero, with no material regression in correct no-match behavior. If quality does not justify a clear choice, use operational evidence and prefer the simpler implementation when it is cheaper or faster. Lack of a significant difference is not proof of equivalence.

The fixed-state comparison identifies decision quality; the full-flow comparison can veto a choice that introduces substantial clarification burden or failures. Human findings, if collected, may change the product recommendation; explain discrepancies instead of hiding them. Automated-only evidence supports a **provisional** product choice. Small samples or wide intervals may legitimately produce “inconclusive.”

Set `DECISION_METHOD` from the recommendation and record the reason. Keep the Clef adapter and its experiment evidence even if the LLM baseline wins. Technical expertise is demonstrated by a sound test and response to evidence, not by requiring a particular model to win.

## 4. Founder-facing results report

After actual experiments, generate `Beli_Group_Explore_Experiment_Report.md` and a polished, presentation-ready PDF of about 4–6 pages, with an appendix if necessary. Render and visually inspect the PDF before delivery. This report is a required project deliverable, not an optional summary in chat.

The first page must answer: **Which method performed better, by how much, on what evidence, and which should this prototype use?** State whether that answer is provisional or inconclusive. If experiments are blocked, produce a clearly labeled pending report identifying the missing evidence, with no numeric result placeholders that look measured.

Include:

1. An executive recommendation with sample sizes, the primary comparison, uncertainty, and the latency/cost tradeoff.
2. A compact architecture comparison explaining where Clef was used, what was shared, and why the experiment was fair.
3. A side-by-side scorecard of actual quality, raw and delivered constraint failures, no-match behavior, clarification burden, p50/p95 latency, reliability, and cost. Mark missing human review as “not collected.”
4. Two or three exportable charts: quality difference with uncertainty, latency/cost comparison, and a scenario-family breakdown where useful. Label every denominator and distinguish model-judged from human-reviewed results.
5. At least three traced cases: a Clef win, a baseline win, and a failure or infeasible case **if those occurred**. If a category never occurred, say so; do not fabricate a convenient example. Explain what caused the difference and what was learned.
6. Limitations: small curated NYC corpus, synthetic profiles/scenarios, simulated availability, approximate travel, subjective fit judgments, and lack of measured real dining satisfaction unless studied.
7. The chosen product architecture and the next validation step, tied to findings rather than a generic AI roadmap.
8. A reproducibility appendix with snapshot/protocol hashes, model identifiers/settings, prompt versions, timestamps, run counts, command to reproduce, pricing sources, and references to raw results.

Write for founders assessing product and engineering judgment. Explain how gains or weaknesses affect users. Avoid unsupported claims that this improves Beli retention or revenue. Do not assert “Clef is better” based on vendor benchmarks or one handpicked demonstration.

Save raw run logs as JSONL, aggregate metrics as CSV, the protocol/manifest as JSON, and the blinded human-review packet separately. These are experiment outputs, not additions to the participant UX. Record observable inputs, decisions, distributions, timings, and evidence references; do not require private model chain-of-thought.

## 5. Experiment acceptance criteria and deliverables

- A versioned protocol and frozen dataset manifest exist before held-out runs, with explicit development/test separation and no tuning on the final test set.
- Both methods use the specified shared data and equivalent product capabilities. Actual runs, errors, guard rejections, timings, and costs are retained.
- The fixed-state and complete-flow comparisons are reported separately, with actual sample sizes and independent scoring. Clef scores and model self-assessments are never evaluation ground truth.
- The architecture recommendation follows the precommitted rule, identifies uncertainty, and is marked provisional when based only on automated judgments.
- The founder-facing report exists as Markdown and a visually reviewed PDF. Missing provider access, usage data, or human review is explicitly identified.
- The default decision method is set from the supported recommendation, while both adapters remain available for reproduction.

Required output files:

| Output | Purpose |
| --- | --- |
| `experiment/protocol.json` | Frozen methods, metrics, thresholds, run counts, budget, and analysis policy |
| `experiment/dataset_manifest.json` | Snapshot hashes, scenario split, fixture values/seeds, and provenance |
| `experiment/results/runs.jsonl` | Observable run records, including failures and retries |
| `experiment/results/metrics.csv` | Aggregate comparisons, denominators, and uncertainty |
| `experiment/review/blinded_review_packet.md` | Method-blinded human assessment material; record actual responses separately if collected |
| `Beli_Group_Explore_Experiment_Report.md` | Founder-facing report with supported conclusions |
| `Beli_Group_Explore_Experiment_Report.pdf` | Presentation-ready export of the report |

Keep prompts, evaluation code, and reproduction commands in the project alongside these outputs. Do not require private model chain-of-thought. If no real provider runs are possible, create a plainly labeled pending report and list the specific access blocker; fixture runs do not satisfy the experiment acceptance criteria.

## 6. Coding-agent execution instructions

Implement the product and both adapters from the PRD first. Use development scenarios to improve prompts, rubrics, safeguards, and the clarification/host policy. Then freeze this protocol's concrete settings, run the paired tests, analyze independently, and generate the report.

Human review may follow the automated analysis. Prepare the blinded packet and finish a provisional automated report while feedback is unavailable. Never fabricate reviewer responses. If human findings later change the recommendation, version the report and explain the difference.

Treat the report as a required delivery artifact. Present the recommendation, practical user implications, limits of the evidence, and reproduction command together with the working prototype. Do not send the report to Beli or other recipients unless the user separately instructs you to do so.
